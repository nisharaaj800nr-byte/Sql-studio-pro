SQL Studio Pro ko complete SQLite 3 IDE banana hai.

Goal:
SQLite ke liye koi valid query unsupported nahi rehni chahiye, jab tak woh installed device SQLite engine ke limitation ki wajah se unavailable na ho. Query actual local device database par execute honi chahiye. Internet/API server core SQL execution ke liye required nahi hona chahiye.

Implement and verify complete SQLite support:

1. Query types
- SELECT
- INSERT
- UPDATE
- DELETE
- REPLACE
- UPSERT / INSERT ... ON CONFLICT
- WITH and recursive CTE
- JOIN, LEFT JOIN, CROSS JOIN
- UNION, UNION ALL, INTERSECT, EXCEPT
- Subqueries and correlated subqueries
- GROUP BY, HAVING, ORDER BY
- CASE expressions
- Window functions
- Aggregate functions
- Date/time functions
- String, numeric, conditional and NULL functions
- JSON functions when supported by the device
- CAST and COLLATE
- FILTER and OVER clauses where supported

2. Schema and DDL
- CREATE TABLE
- CREATE TABLE AS SELECT
- ALTER TABLE rename table
- ALTER TABLE rename column
- ALTER TABLE add column
- DROP TABLE
- CREATE INDEX

- DROP INDEX

- DROP TRIGGER
- Foreign keys
- CHECK constraints
- UNIQUE constraints
- PRIMARY KEY
- AUTOINCREMENT
- DEFAULT values
- Generated columns where supported
- WITHOUT ROWID tables where supported
- STRICT tables where supported

4. Execution behavior
- Run queries through actual expo-sqlite on native devices.
- Keep all core database operations local and offline.
- Correctly detect read, write, DDL, PRAGMA, transaction, and explain queries.
- Support bound parameters safely.
- Never interpolate user values directly into SQL.
- Correctly handle quoted strings, quoted identifiers, comments, trigger bodies, and semicolons.
- Support multiple SQL statements where expo-sqlite safely permits it.
- If a multi-statement query cannot be executed by the native API, split it with a real SQL-aware tokenizer, not a simple semicolon split.
- Return rows, columns, affected row count, last inserted row ID, execution duration, and truncation status.
- Preserve transaction state between statements.
- Do not silently auto-commit user transactions.
- Do not leave transactions open after errors unless the user explicitly started one.
- Handle empty results without crashing.
- Handle large results with pagination or row limits.
- Show a clear message when output is truncated.
- Handle invalid SQL as a user-facing error instead of crashing the app.

5. Schema-aware autocomplete
- SQLite keywords
- Tables
- Views
- CTE names
- Columns
- Aliases
- Functions
- Pragmas
- Indexes
- Trigger names
- Foreign-key relationships
- JOIN suggestions
- Suggestions must use the current database schema.
- Cache schema metadata and invalidate it after DDL changes.
- Debounce autocomplete so typing remains responsive.
- Insert selected suggestions without corrupting existing SQL.

6. Diagnostics
Show precise errors with line and column where possible:

- Syntax errors
- Unknown table
- Unknown column
- Unknown function
- Ambiguous column
- Invalid constraint
- Foreign-key violation
- UNIQUE violation
- NOT NULL violation
- CHECK violation
- Locked database
- Busy database
- Read-only database
- Corrupt database
- Incorrect parameter count
- Unsupported SQLite feature
- Invalid transaction state

Warnings:
- DELETE without WHERE
- UPDATE without WHERE
- DROP TABLE
- DROP INDEX
- ALTER TABLE
- VACUUM
- ATTACH DATABASE
- SELECT *
- Missing LIMIT in data browsing mode
- Possible Cartesian JOIN
- Possible full-table scan
- Large result set
- Destructive PRAGMA
- Query running inside an active transaction

Warnings should not block safe queries unnecessarily. Destructive statements must require confirmation where appropriate.

7. Device-local support
- Use expo-sqlite as the native source of truth.
- Database files must persist across app restarts.
- Multiple local databases must work.
- Opening and closing databases must not leak connections.
- App background/foreground transitions must be safe.
- Offline mode must support opening databases, reading, writing, transactions, imports, exports, and query history.
- Do not send database contents to the API server.
- AI must remain optional and must never be required for SQL execution.
- Preserve existing corrupt-database recovery.
- Clearly show native SQLite version and supported compile-time features in Settings/About.

8. Query editor UX
- Syntax highlighting for SQLite keywords, functions, strings, comments, numbers, identifiers and operators.
- Current-line highlight.
- Matching bracket highlight.
- Error-line highlight.
- Inline warning markers.
- Query validation before execution.
- Run, stop/cancel if supported, format, explain, save and export controls.
- Loading, success, empty, error, warning, timeout and truncated states.
- Keyboard shortcuts on web and usable touch controls on mobile.

10. Explicit limitation behavior
Do not claim that PostgreSQL, MySQL, SQL Server or Oracle syntax is supported by SQLite.

If the user enters another dialect:
- Detect common dialect-specific syntax.
- Show a clear warning such as:
  "This is PostgreSQL syntax. SQL Studio Pro currently executes SQLite queries locally."
- Do not silently rewrite the query.
- Do not silently send the query to the server.
- Keep the SQLite engine reliable first.
